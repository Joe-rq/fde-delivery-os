# Eval 与验收

## Eval 是交付合同的一部分

评估集要在开发早期建立，不是在项目末尾证明“我们做得不错”。它同时定义：

- 什么叫好；
- 哪些错误可以接受；
- 哪些错误必须转人工；
- 迭代是否真实变好；
- 是否达到试运行或扩大的门槛。

## Eval 是主控回路，不是第 7 步的终点

把 Eval 当作十步闭环里做完就交付的一站，会漏掉它真正的用途：驱动迭代。每次改动（改 prompt、换模型、调工具、改流程）都要对照评估判断「是否真的变好」，而不是靠感觉。

借「外挂训练」的类比理解四个陷阱：

| 陷阱 | 含义 | 对应纪律 |
|---|---|---|
| 过拟合 | Eval 分数涨，但真实体验没改善 | 不要围着锁定样本反复调参 |
| 测试集污染 | 围着 eval 集改代码，eval 失效 | 调参和评测用不同样本 |
| 数据飞轮 | Agent 上线改变用户行为，旧样本失效 | 给 eval 集设刷新率，持续从生产回流 |
| 生成便宜验证贵 | 投入瓶颈在验证不在生成 | 把资源压在评测和回流 |

Eval 因此贯穿第 6–10 步：原型 → 评测 → 改动 → 再评测 → 发布 → 从生产失败更新评测 → 回到基线。

## 四层评估

| 层 | 关注 | 示例 |
|---|---|---|
| 单元 | 确定性逻辑 | 规则、金额、权限、格式 |
| 任务 | 单个业务任务结果 | verdict、字段、引用、工具调用 |
| 流程 | 多步闭环 | 覆盖、恢复、幂等、人工接管 |
| 业务 | 真实使用结果 | 耗时、采纳、风险、产能 |

## 三类评审器

- 代码评审器：规则、结构、数值、状态等可确定判断。
- 模型评审器：语义质量、解释完整性等需 rubric 的判断。
- 人工评审器：高风险、业务偏好、责任和边界案例。

能确定性验证的，不优先交给模型判断。

## 最小 Eval 包

1. 代表性真实样本和边界样本。
2. 标准答案或业务 rubric。
3. 指标定义、分母、阈值和置信区间说明。
4. 错误分类：数据、检索、规则、模型、工具、权限、流程。
5. 人工升级策略和不可自动化项。
6. 回归频率、版本记录和发布门。

## 测试集是活资产

测试集不是建好不变的快照，而是要主动治理的活资产。六种迭代动作：

| 动作 | 何时做 |
|---|---|
| 新增 | 发现新的真实失败模式 |
| 升级加严 | 原本过的样本现在该更严 |
| 降级为只观测 | 暂不卡门但继续看趋势 |
| 调整权重 | 改变案例重要性，不改正例 |
| 重新标注 | 业务标准变了 |
| 退役不删 | 过时但保留可回溯，防重蹈覆辙 |

退役的样本不删除，保留历史可回溯；锁定回归集才允许上线。

## Agent 三类高隐蔽失败

传统 review 容易漏掉 Agent 特有的三类失败，因为它们看起来「没错」：

| 失败类型 | 表现 | 最小检测 |
|---|---|---|
| 静默失败 | 错误极其流畅自然，不对真值核对看不出 | 必须对真值逐条核对 |
| 局部全对整体失败 | 每步逻辑对，但业务约束错 | 引入领域专家做业务约束评审 |
| 回归塌陷 | 修一处塌另一处 | 跑锁定回归集才允许上线 |

错误分类（数据/检索/规则/模型/工具/权限/流程）回答「错在哪层」；这三类回答「为什么 review 没发现」。

## 企业 AI 技术红线

- 没有评测集，不进生产。
- 没有明确人工复核策略，不写入关键系统。
- 没有追踪、失败分类和回滚，不扩大上线。
- 没有采用观测，不宣布业务成功。

启衡 **FDE 课程沙盒 PoC / 合成数据** 的本地摘要显示：30 条样本中 27 条的最终判定与违规代码同时一致。这个 90% 不能外推为生产指标，且原始数据未公开；它的公开价值只是说明好的 Eval 要指出差异来自数据、规则、模型、工具还是流程，并给出下一步工程动作。
