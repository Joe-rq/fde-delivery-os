# 第二课 · 项目范围界定 + CLI工作流 + SOW

> **来源**：FDE 共学营第一期。本页只记录受课程启发的方法论骨架与项目映射，**不复制课程正文、PPT 或讲义**。课程原始内容受版权保护，公开改编许可未确认，详见 [来源登记](../06-Sources/来源登记.md)。
>
> **覆盖**：PPT 33 页

> **案例口径**：本文提及的「启衡」指启衡 FDE 课程沙盒 PoC（合成数据），非真实客户或生产证据；详见 [来源登记](../06-Sources/来源登记.md)。

## 核心论点

把一条模糊线索推进到可验收原型，靠的不是模型能力，而是三件工程化骨架：先用 SOW 把“怎么算赢”锁成契约，再用可交付闭环（最后 15% 的错误回流）证明价值，再用 CLI 工作流纪律让交付可重复。

## 方法论地图

### FDE 定位与双组织协同（p1-5）

- **要点**：
  - 主线：线索 → 可验收原型，五动作链路，产出 SOW + Demo 两件
  - ToB 本质：供应商与客户两套组织围绕同一业务结果协同
  - FDE 小队跨职能闭环，商务/产品/工程三类角色共担一个结果
  - Palantir 式定位：站在现场与产品之间，锁定问题 → 接数据 → 共建 → 评测 → 回流
- **框架/术语**：五动作链路（PROJECT/DISCOVERY/SCOPE/DEMO/DELIVERY）、供应商五段流水线、FDE 三类角色、Palantir 式闭环
- **项目对应**：[00-Map/FDE交付闭环.md](../00-Map/FDE交付闭环.md)、[00-Map/个人FDE定位.md](../00-Map/个人FDE定位.md)、[00-Map/FDE能力地图与成长路线.md](../00-Map/FDE能力地图与成长路线.md)、[01-Methods/复用飞轮.md](../01-Methods/复用飞轮.md)
- **Gap**：🔧补强 —— 项目是交付侧单视角，缺“双组织协同”对接点与 FDE 小队角色 RACI（个人八维能力不等于团队角色协作模型）。
- **吸收建议**：在 FDE 交付闭环补“双组织协同”节（诊断授权/数据权限/验收签字对接点），新增 FDE 小队角色 RACI。

### 从线索到真实需求（p6-8）

- **要点**：
  - 六步法全程强调可量化、可验收、可复用
  - 客户先买的是“你做得成”的信任证据，证据换诊断而非直接签单
  - 三类证据各解一种疑虑：LOGO / SOLUTION / PEER
  - 按角色看动机，沿真实流程追问五件事
  - 不触及真实流程 = 低价值工具需求
- **框架/术语**：六步法、三类证据（LOGO/SOLUTION/PEER）、动机分层（老板/中层/国企）、流程五问
- **项目对应**：[02-Playbooks/从线索到SOW.md](../02-Playbooks/从线索到SOW.md)、[01-Methods/现场发现与五张地图.md](../01-Methods/现场发现与五张地图.md)、[02-Playbooks/进场诊断Playbook.md](../02-Playbooks/进场诊断Playbook.md)
- **Gap**：🔧补强 —— 流程五问已覆盖；三类证据分类法与决策角色动机锚点（老板/中层/国企）缺失。
- **吸收建议**：把“证据”显式拆成三类并标注各自解决的客户疑虑；现场发现方法补“决策角色动机锚点”小表。

### 项目筛选与经济学（p9）

- **要点**：
  - 四维筛选：动流程 / 一把手 / 算清价值 / 能沉淀
  - 成本基准：3 人半月约 5-6 万仅覆盖成本，10 万+ 才有合理利润
  - 优先做能反哺垂类底座的项目
- **框架/术语**：四维筛选、成本基准（3 人半月 / 10 万门槛）、垂类底座反哺优先
- **项目对应**：[01-Methods/项目机会筛选.md](../01-Methods/项目机会筛选.md)、[03-Templates/机会评分卡.md](../03-Templates/机会评分卡.md)
- **Gap**：⚠️缺口 —— 筛选维度已覆盖且更细，但缺 FDE 项目经济学/定价基准模型（评分卡无成本/报价字段）。
- **吸收建议**：项目机会筛选新增“FDE 经济学速算”小节（人天×团队×周期×利润率 → 报价区间），评分卡补成本测算与建议报价两列。

### SOW：从量化到变更管理（p10-14）

- **要点**：
  - 73% 失败项目事先无成功定义；有量化成功率约 4.5 倍
  - 边界三问：给谁演示 / 那屏数字 / 基线与变更

  - AI 效果三阶段：离线评测 → 试运行 → 生产稳定性
  - 锁死基线 vs 迭代空间分明
  - 变更闭环四步：基线 → 试运行 → 变更单 → 双方确认
- **框架/术语**：73%/4.5 倍锚定、边界三问、打动点（那屏数字）、指标来源捷径、AI 效果三阶段、SOW 五大块、锁死基线 vs 迭代空间、变更闭环四步、SOW/SPEC/Code 三件递进

- **Gap**：🔧补强 —— 大部分已覆盖且更细；缺“打动点倒排优先级”显式概念、成功率锚定引用、带变更单工件的四步闭环（现分散在 SOW 模板 + Eval 门）。
- **吸收建议**：证据链补“打动点倒排优先级”与成功率锚定引用；SOW 模板变更机制节整合变更单工件，03-Templates 补变更单示例。

### 从可演示到可生产：最后 15%（鞋服案例 p15-18）

- **要点**：
  - 整体效果好 ≠ 可交付，难度集中在最后 15%
  - 85% → 95% 靠规则 + 数据 + 评测 + 反馈四者循环
  - 可交付闭环四要素：客户标准 → 可执行规则 → 真实数据验证 → 错误回流
  - 隐性经验 → 可执行、可标注、可校验的规则文本
  - 交付复利 + 获客飞轮：交付结果转同行证据
- **框架/术语**：最后 15%、85%→95%、可演示 ≠ 可生产、可交付闭环四要素、隐性经验 → 可执行规则、交付复利结构、获客飞轮
- **项目对应**：[01-Methods/SOW-Spec-Demo证据链.md](../01-Methods/SOW-Spec-Demo证据链.md)、[02-Playbooks/从原型到生产.md](../02-Playbooks/从原型到生产.md)、[04-Cases/启衡课程沙盒报销预审PoC.md](../04-Cases/启衡课程沙盒报销预审PoC.md)、[01-Methods/复用飞轮.md](../01-Methods/复用飞轮.md)
- **Gap**：⚠️缺口 —— sandbox 案例已实践这套闭环，但方法层未把“可交付闭环四要素 + 最后 15%”提炼成命名模型，只有一句“Demo 不能补丁成生产”。
- **吸收建议**：把“可交付闭环四要素”提炼进 01-Methods（证据链姊妹篇或从原型到生产扩展节），用启衡报销案例做内嵌实证。

### CLI 工作流纪律（p19-24）

- **要点**：
  - 网页 AI 撞四道墙：不能读代码库 / 执行命令 / 访问内网 / 被脚本编排
  - 三工具分工：Claude Code（长上下文工作流）/ Codex CLI（CI 批量）/ Cursor（重度改码）
  - 通用起手式四步：上下文文件 → SOW 到 SPEC → 小步增量 → 每步自证
  - CLI 五类日常动作：读存量 / 接系统 / 动系统 / 无人值守 / 多模态摄取
  - AGENTS.md 已成事实规范（课程引用的外部统计：6 万+ 项目、AAIF 治理；非课程原创数据）
  - 人机规模三档：盯屏 3-5 / 异步 10-60 / fan-out 数百
  - 4 倍产能但净增益仅 12%，瓶颈在 review 不在生成
  - 脚手架 > 模型；永不从聊天记录直接改代码
- **框架/术语**：网页 AI 四道墙、CLI 三工具分工、通用起手式四步、CLI 五类日常动作、AGENTS.md 规范 / AAIF 治理、人机规模三档、4 倍 vs 12% 净增益、脚手架 > 模型、四条工作流纪律

## 本课最值得吸收的点

1. **CLI 工作流纪律层整块缺失**：项目 05-Engineering 是运行时架构，缺“人怎么指挥 CLI Agent 干活”的日常纪律——四道墙选址论证、三工具分工、五类日常动作、AGENTS.md 上下文先行（仓库根本身没有）、人机规模经济学（三档 + 4 倍产能但净增益仅 12% 的 review 瓶颈）、四条护栏纪律。这是 FDE 日常方法论的空白层。
2. **可交付闭环四要素 + 最后 15% 尚未命名**：sandbox 已实践（模糊审单 → 三态规则 → Eval → 定向 L2 复核消错），但方法层只有一句“Demo 不能补丁成生产”。应把“客户标准 → 可执行规则 → 真实数据验证 → 错误回流”显式命名，并补“85% ≠ 可交付”认知锚点。
3. **Demo 现场铁律 + Demo 工厂化缺失**：有“最短证据链”路径概念，无现场操作纪律（状态标注 / 异常可演示 / 时间盒 ≤ 3 分钟降级）、演示任务卡五要素、Demo 工厂六步。ChatDemo 应从外部资源内化为 Playbook。
4. **获客三类证据分类法缺失**：从线索到 SOW 只笼统说“用一页案例换诊断”，未拆 LOGO / SOLUTION / PEER 三类，未标注各自解决的客户疑虑。PEER 型最易触发预算，对报价策略有直接价值。
5. **FDE 项目经济学 / 定价基准缺失**：Economics 维度只有“覆盖成本风险利润”定性描述，评分卡无成本/报价字段。课程给的 3 人半月约 5-6 万、10 万+ 才有合理利润、优先反哺垂类底座，是判断“值不值得打”和报价的直接依据。

## 溯源补遗（2026-08-08 对照文字稿后补录）

文字稿答疑节、原笔记漏录的定位澄清：

- **FDE vs 解决方案架构师**：都做翻译；SA 偏「需求 → 可销售可配置的标准方案 + 行业共性」，FDE 偏「需求 → 可部署可运行、可被真实用户使用的产品结果」。两者随 Demo/现场交付权重上升而重叠。
- **FDE ≠ 外包**：分界不在驻场，而在是否参与问题定义、对业务结果负责、把现场交付沉淀回可复用产品。什么项目都接、只按时间收费且无沉淀 → 退化为外包。
- **是否单独付费**：国内招标罕有明确「配置 N 名 FDE」，FDE 多是降本提效的组织/工作方式；能否单独收驻场咨询费取决于客户类型、供应商资质、项目价值。
- **不必先做本体**：重型 Ontology 适合数据成熟的大型企业；中小企业先建清晰的知识/语义/工作流层即可，过早建本体只增成本。
- **非技术背景转 FDE**：从商务型/产品型切入，但仍须具技术判断（Demo↔生产差距、数据/安全/接口/评测风险）；工程背景则须补业务观察与客户沟通。
