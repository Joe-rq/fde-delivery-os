# 从原型到生产

## 原型阶段

只证明最关键的 1–3 个假设：

- 真实数据是否可用；
- 核心任务质量是否达到最低线；
- 系统是否能接入真实入口和输出；
- 用户是否愿意完成这条路径。

每个假设都要有测试、结果和结论。

## 进入试运行前的重构门

不要默认沿用 Demo 架构。重新检查：

- 数据、身份、权限和审计；
- 失败、超时、重试、幂等和恢复；
- 模型版本、Prompt、规则和 Eval 的版本化；
- 敏感字段、数据出域和日志脱敏；
- 人工复核、override 和最终责任；
- 运行成本、延迟和容量；
- 部署、回滚、Runbook 和支持责任。

> 重构门实例（私有证据）：某产品 Word 模板规范生成从 Demo 到生产必须过重构门。Demo 直接生成 docx 会丢失 logo / footer / 多级编号；生产改用 Base-Replace 策略--复制模板底文件、清空 body、保留 `<w:sectPr>`，再用模板自带样式追加内容。典型坑：python-docx 的 OxmlElement XML 在 `save` 序列化时被丢弃，页码须用高层 API 写入；LibreOffice 不尊重空 footer，仍渲染页码，需 `save` 后 ZIP 后处理移除 `footerReference`；简版编号不显示，须在每个段落显式加段落级 `numPr`。教训：Demo 架构到生产必须经重构门，否则丢品牌资产与编号链。[Private-evidence · 核验于 2026-05~06 · 不可由本仓库独立复算]

## 分阶段上线

1. Shadow：只旁路观察，不影响正式流程。
2. Pilot：少量真实用户，人工逐项复核。
3. Limited：限定团队、任务类型和权限。
4. Full：达到质量、稳定、采用和运维门槛后扩大。

## 每阶段的升降级条件

同时定义：

- 升级：哪些指标达标才扩大。
- 降级：哪些错误触发转人工、关闭写操作或回滚。
- 停止：哪些风险出现必须中止。

生产化不是“功能更多”，而是系统在坏数据、坏网络、坏输入和人离场时仍然可解释、可恢复。
