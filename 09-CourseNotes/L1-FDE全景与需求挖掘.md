# 第一课 · FDE全景+企业需求挖掘

> **来源**：FDE 共学营第一期。本页只记录受课程启发的方法论骨架与项目映射，**不复制课程正文、PPT 或讲义**。课程原始内容受版权保护，公开改编许可未确认，详见 [来源登记](../06-Sources/来源登记.md)。
>
> **覆盖**：PPT 20 页

## 核心论点

模型能力就绪后，价值实现的瓶颈已从模型本身转移到部署落地；FDE 的本质是把 AI 从"会说"变成"会做成"——在门槛已降、需求未饱和、组织未定型的窗口期内，识别哪个行业哪个流程值得做、并端到端对运行结果负责，比写代码本身更稀缺。

## 方法论地图

### FDE 起源：Palantir 范式与三条准则（页 1-4）

- **要点**：
  - Palantir 2003 年首创，工程师驻场把业务建模进平台并直接上线
  - "实施即产品"：客户定制被抽象回平台能力，交付即研发、粘性极高
  - 三准则：对运行结果负责 / 需求来自一线 / 可突破产品边界
- **框架/术语**：FDE、Palantir 三准则、实施即产品（Delivery-as-Product）
- **项目对应**：[复用飞轮](../01-Methods/复用飞轮.md)、[FDE 交付闭环](../00-Map/FDE交付闭环.md)、[FDE 资源矩阵](../08-Resources/FDE资源矩阵.md)
- **Gap**：🔧补强——操作层体现了"对结果负责"精神，但未把起源与三准则作为显式定位叙事写下，缺"这个角色凭什么这样干"的源头框架。
- **吸收建议**：在 [个人 FDE 定位](../00-Map/个人FDE定位.md) 或新建 `00-Map/FDE起源与准则.md` 中，用自己话补一段起源叙事 + 三准则表述，作为方法论合法性锚点。

### 大模型厂的部署瓶颈与交付自建（页 5-7）

- **要点**：
  - 瓶颈已从模型本身转移到部署落地
  - 通用模型交付不了的根因：通用 vs 特定 / 概率性输出 / 需求模糊 / 生产化工程缺口
  - 模型厂"交付即业务"：收入看客户实际实现的价值；MCP 本质是 FDE 手工接入的标准化
- **框架/术语**：部署瓶颈转移、四类结构性困境、Deployment Company、MCP
- **项目对应**：[FDE 资源矩阵](../08-Resources/FDE资源矩阵.md)（OpenAI 岗位、MCP）、[来源登记](../06-Sources/来源登记.md)
- **Gap**：🔧补强——项目是工具使用者视角，缺"为什么模型厂必须自建交付力量"的供应链判断，也缺 Deployment Company 这类组织化信号。
- **吸收建议**：在 [本地研究主题索引](../08-Resources/本地研究主题索引.md) 补一条"FDE 供应方格局"研究主题，只记公开可核验事实。

### 云厂商补课与渠道商缺位（页 8-9）

- **要点**：
  - 云厂比模型厂晚 1-2 年，战略层怕被压回基础设施低毛利
  - 四项约束：商业模式冲突 / 路径依赖 / 紧迫性不足 / 组织形态
  - 集成商无法承接 FDE 的五类原因；渠道是被重组而非取代
- **框架/术语**：云厂商补课式交付、集成商无法承接的五类原因、渠道重组
- **项目对应**：无
- **Gap**：⚠️缺口——项目纯聚焦交付方法本身，没有任何云厂商 / 渠道商 / 集成商在 FDE 生态中位置的判断。
- **吸收建议**：不建议塞进操作文档；若补，放在 [本地研究主题索引](../08-Resources/本地研究主题索引.md) 作为"FDE 生态方格局"研究 backlog，用于判断个人 / 小团队卡位。

### Solo FDE：最小作战单位与能力重心迁移（页 10）

- **要点**：
  - 工具成熟 + 成本下降，使 Palantir 团队级工作可由 1-3 人承担
  - 中美分化：美 services-as-software；中私有化部署 + 数据散落在钉钉飞书企微用友
  - 稀缺能力从"工程实现"转向"行业进入与需求识别"
- **框架/术语**：Solo FDE、services-as-software、能力重心迁移
- **项目对应**：[个人 FDE 定位](../00-Map/个人FDE定位.md)
- **Gap**：🔧补强——定位讲了"我是谁"，缺"为什么现在个人能做"的结构性判断（门槛下降 / 窗口期 / 能力重心迁移）。
- **吸收建议**：在 [个人 FDE 定位](../00-Map/个人FDE定位.md) 补一节"Solo FDE 成立前提"，用自己话重述门槛下降 + 窗口期 + 能力重心迁移三点。

### FDE 全景图与窗口期判断（页 11）

- **要点**：
  - 五类玩家：Palantir 驻场 / 模型厂自建 / 云厂补课 / 渠道商转型 / 个人小团队
  - 四条趋势线：角色验证 → 需求扩大 → 门槛下降 → 窗口有限
  - 最佳时机三条件同时成立：门槛降 / 需求未饱和 / 组织未定型
- **框架/术语**：五类玩家全景图、四条趋势线、窗口期三条件
- **项目对应**：无
- **Gap**：⚠️缺口——项目是 how 手册，缺"为什么是现在"的宏观叙事与窗口期判断框架。
- **吸收建议**：若需对外讲清价值，在 `00-Map` 或 [07-Portfolio](../07-Portfolio/) 补一页"FDE 窗口期判断"，标注为判断而非事实。

### 企业客户分类矩阵：决策层认知 × 组织复杂度（页 12）

- **要点**：
  - 二维矩阵：决策层认知 A1-A4 × 组织复杂度三档
  - 一把手 AI 意识决定转型步伐，认知比规模更要命
  - A3/A4 是能掏钱出结果人群；中型组织最易冒出标杆
- **框架/术语**：认知 × 复杂度矩阵、认知四档（A1-A4）、组织复杂度三档
- **项目对应**：[项目机会筛选](../01-Methods/项目机会筛选.md)（PSF 三关 + 十维评分）、[机会评分卡](../03-Templates/机会评分卡.md)
- **Gap**：⚠️缺口（重要）——项目有"项目级"筛选，缺"客户级"战略分层；矩阵决定 Discovery 之前该不该进场、找谁谈、用什么节奏。
- **吸收建议**：在 [项目机会筛选](../01-Methods/项目机会筛选.md) 的 PSF 三关之前补一节"客户分层"，重述认知 × 复杂度矩阵作为战略预筛。**本课最值得吸收的单点。**

### 通用大模型的五项结构性局限（页 13）

- **要点**：
  - 五项局限：无执行 / 缺企业上下文 / 单轮 / 数据缺位 / 输出不可靠
  - 大模型只有大脑，缺手脚、记忆、问责（对应 Agent 四大支柱缺位）
  - 企业为结果付费，对话形态无法交付结果
- **框架/术语**：通用大模型五项结构性局限、大脑缺手脚 / 记忆 / 问责
- **项目对应**：[Production-Agent 参考架构](../05-Engineering/Production-Agent参考架构.md)（任务-机制表、七层结构）
- **Gap**：🔧补强——项目有给工程师看的选型逻辑，缺面向决策层 / 客户的说服性框架。
- **吸收建议**：把五项局限改写成"通用大模型为什么交付不了结果"客户沟通卡，放进 [进场诊断 Playbook](../02-Playbooks/进场诊断Playbook.md) 或 [从线索到 SOW](../02-Playbooks/从线索到SOW.md) 的"对齐认知"环节。

### Agent 能力演进与生产级四大支柱（页 14）

- **要点**：
  - 演进：AutoGPT（2023）→ 工具调用稳定（2024 下半年）→ MCP（2024.11）→ computer use（2025）
  - 四大支柱：规划 / 工具调用 / 循环自我修正 / 记忆上下文
  - 别用 2023 年 AutoGPT 的失败判断今天的可用性
- **框架/术语**：Agent 能力演进时间线、生产级 Agent 四大支柱
- **项目对应**：[Production-Agent 参考架构](../05-Engineering/Production-Agent参考架构.md)（七层结构）、[本地研究主题索引](../08-Resources/本地研究主题索引.md)
- **Gap**：✅已覆盖——项目七层结构与生产最小要求已涵盖四大支柱且更细。
- **吸收建议**：无需补充。可选地在参考架构加一行能力演进关键节点注脚，帮读者校准"用旧案例判断今天"的认知偏差。

### 企业级 Agent 落地四难点（页 15）

- **要点**：
  - 键鼠能做的 Agent 理论都能覆盖，卡点是落地而非能力
  - 四难点：业务 know-how / 数据 / 组织 / 决策层认知
  - 屏幕前三环节：获取信息 → 作判断 → 操作系统
- **框架/术语**：落地四难点、屏幕前三环节
- **项目对应**：[现场发现与五张地图](../01-Methods/现场发现与五张地图.md)、[进场诊断 Playbook](../02-Playbooks/进场诊断Playbook.md)
- **Gap**：✅已覆盖且更细——项目五张地图（流程 / 数据 / 系统 / 组织 / 政治）直接对应并细分了四难点。
- **吸收建议**：无需补充。项目已用五张地图超越了课程颗粒度。

### FDE 核心能力：四能力对四难点与端到端职责（页 16-17）

- **要点**：
  - 能力 ↔ 难点一一对应：需求识别 ↔ know-how；工程 + 评估 ↔ 数据；跨层沟通 ↔ 组织 / 认知
  - 需求识别 = 把隐性知识显性化，比写代码更难更值钱
  - FDE 对运行结果负责，必须含真实环境构建 / 评估 / 组织配合 / 可复用沉淀
  - 铁律：诊断在前，构建在后
- **框架/术语**：四能力对四难点映射、六个能力模块、诊断在前构建在后、隐性知识显性化
- **项目对应**：[FDE 能力地图与成长路线](../00-Map/FDE能力地图与成长路线.md)、[FDE 交付闭环](../00-Map/FDE交付闭环.md)、[进场诊断 Playbook](../02-Playbooks/进场诊断Playbook.md)、[生产化与采用](../01-Methods/生产化与采用.md)
- **Gap**：🔧补强——八维能力 + 十步闭环比课程更系统，但缺一张"哪个能力解哪个难点"的显式对照表。
- **吸收建议**：在 [FDE 能力地图](../00-Map/FDE能力地图与成长路线.md) 补一张"八维能力 ↔ 五张地图 ↔ 落地难点"显式映射表，无需新增能力维度。

### Solo FDE 获客四路径（页 18）

- **要点**：
  - Solo 比团队多一项关键能力：获客（背后无销售 / BD）
  - 四路径按杠杆递增：熟人 → 社群 → 自媒体 → 垂直深耕
  - 垂直深耕边际获客成本最低，是复用飞轮的获客侧印证
- **框架/术语**：Solo FDE 获客四路径、杠杆递增、边际获客成本
- **项目对应**：[个人 FDE 定位](../00-Map/个人FDE定位.md)、[从线索到 SOW](../02-Playbooks/从线索到SOW.md)
- **Gap**：⚠️缺口——项目从"线索"开始讲转化，完全缺"线索从哪来"的获客前置层。对 Solo FDE 是生存层缺口。

### FDE 起步五步法（页 19）

- **要点**：
  - 五步：选有认知行业 → 选可观察流程 → 先人工跑通 → 先定评估集 → 从容错高环节起步
  - 两道护栏：先人工跑通（搞懂业务规则）/ 先定评估集（定义达标）
  - 能力靠真实项目喂养，不靠课程 / 工具学习
- **框架/术语**：起步五步法、两道护栏、能力靠真实项目喂养
- **项目对应**：[进场诊断 Playbook](../02-Playbooks/进场诊断Playbook.md)、[项目机会筛选](../01-Methods/项目机会筛选.md)、[从原型到生产](../02-Playbooks/从原型到生产.md)、[Eval 与验收](../01-Methods/Eval与验收.md)
- **Gap**：🔧补强——要素都有但缺新手编排；项目是给已有项目的人用的，缺给"还没起步"的人的入口。
- **吸收建议**：在 [FDE 能力地图](../00-Map/FDE能力地图与成长路线.md) 或新建 `02-Playbooks/FDE起步路径.md`，把进场诊断 → 机会评分 → 原型 → Eval 编排成新手起步序列，补"选有认知行业""从容错高环节起步"两条指引。

## 本课最值得吸收的点

1. **客户分类矩阵（决策层认知 A1-A4 × 组织复杂度三档）**：项目有机会评分但那是项目级筛选，缺客户级战略分层。补在 [项目机会筛选](../01-Methods/项目机会筛选.md) 的 PSF 三关之前，作为"该不该进场、找谁谈、A3/A4 才是付费人群"的预筛层——本课最值得吸收的单点。
2. **通用大模型五项结构性局限（客户视角）**：项目的任务-机制表是给工程师看的选型逻辑，缺面向客户的说服框架。改写成客户沟通卡放进进场诊断或从线索到 SOW 的"对齐认知"环节，反向引导出 FDE 价值。
3. **FDE 能力 ↔ 落地难点显式映射表**：八维能力和五张地图分开维护，缺"哪个能力解哪个难点"的对照。补一张八维能力 ↔ 五张地图 ↔ 落地难点的显式表放进能力地图。
4. **Solo FDE 获客四路径**：项目从"线索"开始讲转化，完全缺"线索从哪来"的获客前置层。对个人 FDE 是生存层缺口，建议新建获客 Playbook 或在个人定位补一节。
5. **FDE 市场全景 + 窗口期三条件**：项目纯操作层，缺"为什么是现在"的宏观叙事。若需对外讲清价值，可在 `00-Map` 或 [07-Portfolio](../07-Portfolio/) 补一页窗口期判断，标注为判断而非事实。

## 溯源补遗（2026-08-08 对照文字稿后补录）

原笔记漏录、文字稿「先定义问题，再构建最小闭环」节的方法论点（项目话重述）：

- **需求 ≠ 问题**：客户说「想用 AI / 降本增效」只是表层诉求，FDE 须追问真问题——按强度（痛点程度 vs 现有替代是否够便宜方便）、频率（发生频次、是否持续使用）、范围（多少角色/团队面对）、价值（省本/增收/降险）四维评估。可作 [项目机会筛选](../01-Methods/项目机会筛选.md) PSF 三关的需求侧判据。
- **MVP 是最小闭环，非最少功能**：让用户从任务开始走到结果完成；即使仍需人工复核，把 100% 工作压到少量确认即算有价值闭环。
- **企业只为结果付费**：「不会为『接入了 AI』长期付费，只为稳定交付的业务结果付费」——FDE 存在的根本理由，可作客户沟通锚点。
