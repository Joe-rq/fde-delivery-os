# SOW、Spec、Demo 证据链

## 三者边界

| 产物 | 回答 | 不应承担 |
|---|---|---|
| SOW | 商业上答应什么、怎样算赢 | 每个实现细节 |
| Spec | 系统具体怎样实现和验证 | 未经确认的商业扩张 |
| Demo / 原型 | 哪个关键假设被最低成本证明 | 生产稳定性承诺 |

## SOW 范围六问

1. 为什么做：业务目标与 baseline。
2. 做什么：In Scope、P0/P1/P2。
3. 不做什么：Out of Scope。
4. 依赖什么：数据、接口、人员、环境、合规。
5. 怎么证明：样本、指标、容错、试运行、确认动作。
6. 谁来确认：双方负责人、业务专家、数据 owner、验收人。

## 指标四层

| 层级 | 用途 | 合同处理 |
|---|---|---|
| Baseline | 当前表现 | 应记录 |
| Target | 希望达到 | 可作为项目目标 |
| Acceptance | 最低验收线 | 只承诺可控且已验证部分 |
| Business Outcome | 收入、整体降本、风险 | 明确归因边界 |

所有项目都要有指标，但不是所有指标都应立刻成为刚性合同责任。

## 最短证据链

原型只跑一条最能代表价值的路径：

`真实输入 → 关键处理 → 人机判断 → 真实输出/回写 → 指标与证据`

原型完成后，先更新 Spec 和风险，再决定是否进入 MVP。不要把 Demo 代码直接打补丁变成生产系统。

## 从 Demo 到可交付：最后 15%

整体效果好 ≠ 可交付。裁剪、朝向、例外场景这些细节会让生产团队反复返工，交付难度集中在最后 15%——从 85% 到 95% 不是一次调参，而是让规则、数据、评测、反馈循环跑起来。

可交付闭环四要素缺一不可：

| 要素 | 说明 |
|---|---|
| 客户标准 | 把「好看」翻译成可检查的判定规则 |
| 可执行规则 | 隐性经验 → 可标注、可校验的规则文本 |
| 真实数据验证 | 跨 SKU / 案例验证规则稳定性 |
| 错误回流 | 失败样本进入下一轮规则和评测 |

本仓库 [启衡 FDE 课程沙盒 PoC](../04-Cases/启衡课程沙盒报销预审PoC.md)（合成数据）的报销预审已实践这套闭环：模糊审单 → EXEMPTED / RULE_APPLIES / FLAG 三态规则 → Eval → 定向 L2 票面复核消除已知差异。
